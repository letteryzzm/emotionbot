# 统一控制进程

`head.hub_server` 是唯一持有三块 Pico 串口的程序。网页、视觉和 T5 都只提交意图，由它合成后下发。

## 启动

```bash
.venv/bin/python -m head.hub_server        # http://127.0.0.1:8780
ssh -L 8780:127.0.0.1:8780 rog             # 在 Mac 上看 ROG 的网页
.venv/bin/python -m camera.hub_source   # 可选：接摄像头，读 camera.web 的结果
```

启动时只仿真，不打开串口。网页上点“连接真机”才打开。调试台 `tune_server.py` 和控制进程不能同时连接板子。

## 接真机前

1. 关掉 `tune_server.py`，断开舵机 5V，重刷三块板：

   ```bash
   B=/dev/serial/by-id/usb-MicroPython_Board_in_FS_mode
   PATH=$PWD/.venv/bin:$PATH firmware/flash.sh eyes  ${B}_e6616407e368822b-if00
   PATH=$PWD/.venv/bin:$PATH firmware/flash.sh brows ${B}_e6616407e3689e2a-if00
   PATH=$PWD/.venv/bin:$PATH firmware/flash.sh mouth ${B}_e6616407e380b62c-if00
   ```

2. 在调试台记录舵机的实测范围。网页显示“已标定 n/21”，只有这些舵机会被驱动。
3. 下巴必须 JL、JR 都记录，只记录一侧时两侧都不动。

固件没重刷时，“连接真机”会被拒绝。

## 优先级

高优先级只覆盖它写到的舵机，从高到低：

| 来源 | 内容 | 谁写 |
|---|---|---|
| `reflex` | 眨眼 | 控制进程 |
| `manual` | 网页手动 | 网页 |
| `lips` | 嘴型 | T5（待接） |
| `dialog` | 对话情绪 | T5（待接） |
| `vision` | 距离情绪、受惊和视线 | `camera.hub_source` |
| `idle` | 待机视线 | 控制进程 |

全部卸力不走这张表，会直接发 `X`。

## 提交意图

```python
from head.hub_client import HubClient

hub = HubClient()
hub.pose("dialog", "happy", intensity=0.7, ttl=3)
hub.intent("lips", {"JL": 0.4, "JR": 0.4}, ttl=0.2)
hub.clear("dialog")
```

`ttl` 是存活秒数。来源崩溃后意图自动过期，脸回到下一层。

## 保护

| 情况 | 结果 |
|---|---|
| 进程崩溃、USB 断开 | 板子约 1 秒后回 rest，再过 2 秒卸力，然后关闭保护 |
| 控制循环卡住超过 0.5 秒 | 全部卸力并锁定 |
| 某块板不回话或报错 | 全部卸力并锁定，人工检查后重新连接 |
| 网页点“全部卸力”或按 Esc | 立即卸力，要重新连接 |
| 坏命令 | 固件回 `ERR`，整行不执行，主循环不退出 |
| 串口已被别的程序打开 | 拒绝连接；只能发现有权限看到的进程 |
| 连接后别的程序来开串口 | Linux 返回 `EBUSY` |

失联保护只在控制进程连接时打开，`O`、`S` 手动校准默认仍能一直保持。

没有防护的情况：舵机堵转时没有电流检测，固件无法发现；USB 正常但 5V 掉电时，只有板子也重启才会被发现。
